Analysis & Executive Overview1.1 What This Project IsEvoCode asks a specific, testable question: does an evolutionary population of coding-agent configurations — competing, being critiqued, mutating, and passing knowledge forward across generations — resolve more real GitHub issues than a single strong agent that simply iterates on its own output, when both are given the same total LLM call budget. Everything else in the plan (the five agent roles, the genome, the two benchmark tracks, the dashboard) exists in service of answering that one question cleanly.The plan under review is a deliberate rescoping of a much larger original vision (roughly 60–80 named agents across 13 clusters). That original was treated as a design space to mine for ideas, not a build target. What survived is a five-role pipeline whose behaviour — not headcount — evolves, which is the right move for a solo, free-tier, CPU-only build.1.2 Feasibility AssessmentScope: realistic for one person. Five fixed LLM-calling roles (Analyzer, Planner/Coder, Critic, Mutator, Judge) with an evolving configuration genome is a well-bounded system. The heaviest infrastructure item — a Docker-based SWE-bench harness — is pre-built and open source, not something to author from scratch.The free-tier constraint is treated as a first-class design input, not an afterthought. Sizing the population (4–6), generations (3–5), and calls per generation (~4–6) against Groq/OpenRouter rate limits before writing agent code is the single most important decision in the plan — it is what keeps a full experimental run inside a rate-limit budget, and it is very common for student projects to skip this and discover the constraint only after building something too large to run.The comparison is fair by construction. Matching the baseline's call budget to the evolutionary pipeline's is what turns this from a demo into a research result — without it, "evolutionary wins" would just mean "evolutionary used more compute," which reviewers will immediately flag.A null result is pre-authorised. Explicitly framing "no significant difference, but interesting structure in what survives" as a legitimate outcome (Section 2 below) protects the project from feeling like a failure if the primary hypothesis doesn't hold — this is good research hygiene and worth keeping front and centre in the final write-up's framing, not just this planning stage.1.3 Points Worth WatchingA few areas are worth extra attention while building, since they are where free-tier or solo-scale projects most commonly slip:Sample size and statistical claims. 20–30 SWE-bench Lite instances is a defensible subset size for a solo, free-tier project and matches common practice in published work, but differences of one or two resolved instances between the two systems will not be statistically distinguishable. The write-up should report confidence appropriately (e.g. exact resolution counts and a simple binomial/Wilson interval, not just percentages) rather than over-claiming from a small N.LLM-as-judge reliability. The quality/readability/risk score from the Judge role is inherently noisy — the same patch can score differently across calls. Running the Judge call at low temperature and, budget permitting, spot-checking a handful of judged patches by hand strengthens the credibility of that metric in the results chapter.Docker on the development machine. The SWE-bench harness is Docker-heavy; validating it end-to-end on 2–3 known-solved instances in Phase 1 (as planned) is the right order of operations, but it's worth budgeting real time for this — Docker image builds for SWE-bench repos can be slow and disk-heavy on a laptop, and this is a common place for early schedule slippage.Free-tier availability risk. Groq and OpenRouter's free tiers are outside this project's control and can change (rate limits, model deprecation, temporary outages) between now and submission. The provider-abstraction and fallback-model design (Section 4) is the right mitigation; it's worth re-confirming current free-tier limits close to the start of Phase 1 rather than trusting figures gathered at planning time.Dashboard scope creep. The dashboard is explicitly the best demo asset, which makes it tempting to over-invest in. The four scoped views (fitness curve, comparison chart, lineage tree, config-survival view) are the right ceiling — resist adding more once those four exist, since they are what map directly to the two research questions.1.4 Overall VerdictBottom lineThe plan is buildable by one person on free-tier APIs in a 6–8 month window, is framed as a genuine falsifiable research question rather than a build-something-elaborate exercise, and is phased so that a complete, submittable project exists after Phase 5, with Phases 6–7 as safe additive depth. The main execution risks are operational (Docker setup time, free-tier drift) rather than architectural.2. Project Overview2.1 Research QuestionsPrimaryDoes an evolutionary multi-agent pipeline — in which a small population of coding-agent configurations compete, are critiqued, are mutated, and pass knowledge to the next generation — resolve more real-world GitHub issues, and produce measurably better patches, than a single strong agent that iterates on its own output with self-feedback, given the same total LLM call budget?Secondary / exploratoryWhat do agent configurations actually evolve toward over generations — do specific prompt strategies, temperatures, or debate behaviours reliably survive selection, and do the survivors generalise to unseen problems?Success metricsCategoryMetricPrimary% of benchmark instances resolved (tests pass): evolutionary vs. single-agent baseline, same call budget, same modelsSecondaryPatch size/cleanliness vs. gold patch · calls used to reach resolution · wall-clock time · LLM-judged rubric quality scoreExploratoryEvolution trajectories: which configurations survive, what mutates, whether fitness trends up, plateaus, or oscillates2.2 System ArchitectureThe system is built from five fixed agent roles — the code that calls the LLM does not change between individuals. A fixed 20–30 instance subset, spanning a spread of repos and issue types, is used for repeated experimentation; the official Dockerized SWE-bench harness supplies ground-truth pass/fail, so the Judge role never needs to score correctness itself — only quality.Track B — Competitive programming (secondary / stretch)A hand-picked set of 15–25 LeetCode/Codeforces-style problems spanning dynamic programming, graphs, strings, and greedy categories, run through the identical EvoFlow pipeline. The port itself is evidence the architecture generalises beyond a single domain. Dynamic difficulty adjustment and adversarial test generation are clearly-labelled stretch additions here if time allows.2.4 Baseline (Non-Negotiable for the Research Claim)Single-Agent Iterative Refinement: one agent role, same base LLM, generates a solution, receives automated test feedback (pass/fail plus error output), and retries up to N times, where N is chosen so total call count matches the evolutionary pipeline's budget for that problem. An optional random-selection ablation (mutation happens, but selection is random rather than fitness-based) isolates whether selection specifically is doing the work.3. The pipeline is a fixed, small state machine (analyze → propose → critique → mutate → judge → select), not an open-ended agent graph. A generic framework adds abstraction overhead and its own rate-limit/retry assumptions that would need to be fought rather than used. A minimal hand-rolled controller is faster to build correctly for this shape, and — as the original plan notes — comparing it to LangGraph in the write-up remains a valid, gradeable discussion point either way.Why SQLite over a hosted vector database? The memory store only needs to hold a few dozen to a few hundred "lessons learned" records for a solo, free-tier-scale project. A hosted vector DB (Pinecone, Weaviate, etc.) adds an external dependency and, on free tiers, another rate limit to manage — SQLite with a simple cosine-similarity function over stored embeddings is enough and keeps everything in one file that's trivial to inspect, back up, or reset between experiment runs.Why Docker is mandatory, not optional. The SWE-bench harness executes untrusted, LLM-generated code against real repository test suites; Docker isolation is required both for correctness (matching the benchmark's official evaluation environment) and for safety. This is the one piece of infrastructure in the whole stack that shouldn't be simplified further.Keeping the dashboard decoupled from the pipeline. Because the dashboard reads only the JSON Lines log, it can be built and iterated on independently of the agent pipeline, and rebuilt at any point from historical runs — useful if pipeline changes happen late but the dashboard needs to reflect earlier experiments too.4.3 Suggested Repository LayoutPathContents/agents/Prompt templates + calling code for the five fixed roles/evoflow/State machine, scheduler/rate-limiter, evolution controller/memory/SQLite schema, retrieval functions, knowledge-consolidation step/harness/SWE-bench Docker harness integration, Track B sandbox runner/baseline/Single-agent iterative-refinement implementation/dashboard/React/Vite frontend reading the JSON Lines event log/experiments/Run configs, chosen SWE-bench subset list, competitive-programming problem set/logs/JSON Lines event logs per run (gitignored, or sampled runs committed for reproducibility)/notebooks/Analysis notebooks for the results chapter5.
